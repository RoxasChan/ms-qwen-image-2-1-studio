作者：**Roxas Chan** · 邮箱：[6800400@qq.com](mailto:6800400@qq.com)

在浏览器里完成 **文生图 / 图生图 / 图像编辑 / 局部重绘** 四类任务。内置「提示词优化器」：把 Qwen 官方提示词规范原文当作 system prompt 交给大模型，你写中文想法，它按官方规范改写成可以直接提交的提示词。**两条规范分别对应两个对话类型，由你显式选择，不会互相串门。**

## 功能特性

| 能力 | 说明 |
|---|---|
| **文生图 (t2i)** | 输入提示词直接出图，可调尺寸、步数、引导强度、随机种子 |
| **图生图 (i2i)** | 上传参考图（接口上限 **4 张**）+ 提示词，在参考图基础上重新生成 |
| **图像编辑 (edit)** | 用 `<image1>` `<image2>` 标签指名要改的图与要改的属性，只改点名部分 |
| **局部重绘 (inpaint)** | 两种标注方式：**涂抹**白色掩码，或**彩色圈选**（自由圈选 / 矩形框，可多色）把要改的目标套起来 —— **一种颜色对应一条修改指令**，可同时标注多个区域分别处理。支持「涂抹叠加」与「原图 + 独立掩码」两种提交方式 |
| **透明背景素材** | 接口没有输出格式参数（模型恒输出 RGBA 容器），选择透明背景时会按官方模型卡的推荐句式改写提示词 |
| **LoRA 适配器** | 接入接口的 `loras` 参数（最多 6 个、权重和为 1.0）；可直接粘贴魔搭社区链接自动解析出仓库 id，并记住用过的 id |
| **官方 JSON 形态** | 优化结果可查看／复制按官方契约重建的 JSON（t2i 两字段 / edit 三字段）；反过来，把带壳 JSON 粘进创作台会**自动剥壳**，避免 JSON 标点进画面 |
| **提示词优化** | 加载官方规范原文作为 system prompt，多轮对话式改写；**类型（文生图 / 编辑图片）由用户显式指定**，不靠猜；**可锁定参考图让模型真正"看见"画面**；**可选附加规则**（透明图句式 / 主体提取，项目自写、独立成文件）；对话独立保存，可新建 / 重命名 / 删除；超长自动压缩重试 |
| **一次生成多张** | 一次可选 1–4 张。接口**没有**批量参数，所以实际是拆成 N 个独立任务分别提交、**每张各自计费**；每张都用自己的种子（固定种子按张递增，留空则由服务端随机分配），保证不会出成同一张图 |
| **多批并行** | 后台同时可跑多批（默认上限 5，可配），**不必等上一批跑完再提交下一批** |
| **后台任务列表** | 提交后由**服务端**自己轮询、自己落盘，网页只是观察者 —— 关页面 / 刷新 / 重启服务都不丢任务。右栏任务列表显示每批的进度、缩略图与失败原因，可停止跟踪；一批跑完还会用感知哈希报告"本批最像的两张有多像" |
| **生图历史** | 每张图落盘保存，完整记录提示词、尺寸、步数、种子等参数；支持下载、复制提示词、删除 |
| **余额查询** | 直接查 ModelScope 魔豆余额，避免提交后才发现额度不足 |
| **零依赖** | 无 `node_modules`，无构建步骤，无锁文件；只用 `http` / `https` / `fs` / `path` / `crypto` |

## 环境要求

- **Node.js >= 18**（开发与实测环境为 v22）
- 一个 **ModelScope API Key**（[modelscope.cn](https://modelscope.cn) → 个人中心 → 访问令牌，形如 `ms-xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx`）
- 一个现代浏览器

> ⚠️ **这是一个 Node.js 项目，不是 Python 项目。** 请不要执行 `python server.js` —— 那只会得到一个 `SyntaxError: invalid character '—'`，因为文件首行注释里有中文破折号。

## 快速开始

### 1. 获取代码

```bash
git clone <your-repo-url> MS_QwenImage2.1
cd MS_QwenImage2.1
```

### 2. 启动

不需要安装任何依赖，选一种方式即可：

**Windows（推荐）** —— 双击 `start.bat`。脚本会自动切到自身目录、检查 Node 与端口、延迟打开浏览器，端口被占用时会提示是否复用已运行实例。

**任意平台：**

```bash
node server.js
# 或
npm start
```

自定义端口：

```bash
# Linux / macOS
PORT=8080 node server.js

# Windows CMD
set PORT=8080 && node server.js

# Windows PowerShell
$env:PORT=8080; node server.js
```

启动后控制台会打印监听地址，默认 **http://127.0.0.1:5178**。

### 3. 打开界面并配置 Key

浏览器访问 <http://127.0.0.1:5178>，进入左侧 **「个人信息」** 页填入 API Key，点「校验」确认可用后保存。

也可以跳过界面，手工配置文件（见下一节）。

停止服务：Windows 双击 `stop.bat`（会按端口反查并结束进程）；其他平台 `Ctrl+C`。

## 配置说明

配置存在 `data/config.json`，**该文件已被 `.gitignore` 忽略**（含密钥，切勿提交）。首次运行若不存在会自动创建。

从模板复制一份即可：

```bash
cp data/config.example.json data/config.json
```

结构：

```json
{
  "apiKey": "ms-你的-modelScope-密钥",
  "optimizer": {
    "mode": "local",
    "apiKey": "",
    "baseUrl": "https://api-inference.modelscope.cn/v1",
    "model": "Qwen/Qwen3-8B"
  }
}
```

| 字段 | 说明 |
|---|---|
| `apiKey` | ModelScope 访问令牌。**出图与提示词优化都依赖它**（除非优化器单独配了 Key） |
| `optimizer.mode` | 保留字段，当前后端未读取其取值，界面上作为标签展示 |
| `optimizer.apiKey` | 可选。只给「提示词优化」用的 Key；留空则回退到顶层 `apiKey` |
| `optimizer.baseUrl` | 可选。OpenAI 兼容的 chat completions 端点，默认 ModelScope |
| `optimizer.model` | 可选。用于改写提示词的对话模型，默认 `Qwen/Qwen3-8B` |

`baseUrl` 可以指向任何 OpenAI 兼容服务（本地 Ollama、其他厂商网关等），只要该端点支持 `/chat/completions`。

### 环境变量

| 变量 | 默认 | 说明 |
|---|---|---|
| `PORT` | `5178` | 监听端口 |
| `MSQ_DNS_FALLBACK` | `119.29.29.29,1.1.1.1,223.5.5.5` | 本机解析器解析不出某域名时，用来兜底的公共 DNS。设为 `off` 关闭兜底；也可写成自己的列表（逗号分隔）。详见[常见问题](#常见问题)里那两条 DNS 条目 |

## 界面与使用

左侧四个视图：

### 创作台（Studio）

顶部四个模式页签：**文生图 / 图生图 / 图像编辑 / 局部重绘**。

- 提示词、负向提示词
- 尺寸预设下拉（10 个实测可用值，见下表）
- 步数 `steps`（上限 50）、引导系数 `guidance`（1–20）、随机种子 `seed`（−1 ~ 2147483647；留空 = 随机，一次多张时每张会自动分到不同的种子）
- 透明背景开关（**语义开关**：接口无输出格式参数，选它等于按官方句式改写提示词）
- **一次生成张数**（1–4 张，见[下一节](#一次生成多张与后台任务)）
- LoRA 适配器（`loras`，最多 6 个、权重和必须为 1.0）
- 图生图与编辑模式下可拖入 / 多选参考图（接口上限 **4 张**）
- 提交后任务交给后台推进，出图自动落盘并写入历史；若参数被接口钳制或参考图被截断，会当场提示

右侧固定一列**任务列表**，按批次倒序显示每个作业的状态、张数进度、缩略图与失败原因。窗口窄于 1200px 时自动降为上下单列。

尺寸旁会显示字符计数，超过 4000 字符时高亮告警。

#### 一次生成多张与后台任务

**为什么要绕这么大一圈**：ModelScope 的推理接口**只接受单张生成的参数集**（`prompt` / `size` / `steps` / `guidance` / `seed` / `negative_prompt` / `image_url` / `loras`，其余字段一律静默忽略），没有任何 n / batch / count 参数。所以「一次 4 张」在本项目里**就是 4 个独立任务**，而不是一次批量调用。

| 设计点 | 做法 | 原因 |
|---|---|---|
| 并发 | **允许同时跑多批**，只在运行中作业达到上限（默认 5，可用 `MSQ_MAX_RUNNING` 调）时才返回 409 | 早先是"只许一个作业在跑"，第二个提交直接 409。出发点是不让误触变成双倍消耗，但代价是用户想连着出几批必须**干等**，忘了看页面就彻底卡住 —— 那个代价更常发生。上限只是兜住失控 |
| 种子 | 留空时**服务端抽一个基准种子并逐张 +i**，每张都显式发出；填了固定种子同样逐张递增 | 不这么做，N 个请求体一字不差：能不能出不同的图**完全取决于接口对缺省种子的处理**（实测会随机，但那是运气）。而且历史里每张都记 `-1`，看起来就像"四张共用一个种子" |
| 提交节奏 | 逐张串行，间隔 400ms | 同一把 Key 瞬间并发容易触发 429 限流 |
| 落盘位置 | **服务端**，`data/jobs.json` 只存参数与任务 id，**不存图片** | base64 的图动辄几 MB，塞进 JSON 会让读写变成灾难。图片该落在 `outputs/`，历史该进 `history.json` |
| API Key | 作业对象里带一把 `key`，**只在内存**；落盘时显式摘掉 | 提交与轮询必须用同一把 Key。若调用方在请求体里传 Key，只读配置就会变成"提交成功、后台却报 Key 已丢失" |
| 停止跟踪 | 只能停掉**轮询**，任务若已提交给 ModelScope 仍在执行 | 文案不写"已取消"，因为**额度不会退回** —— 写成已取消会让人以为省了钱 |
| 网络抖动 | 单次轮询抛异常时跳过本轮，下一轮再问 | 把偶发失败写成终态是最贵的错误：图还在，却再也没人去取 |
| 服务重启 | 启动时读回未完成的作业，继续轮询 | 任务不因重启而丢失，只是进度可能停在重启前的那一刻 |
| 批内相似度 | 一批跑完后用 **dHash** 量化"最像的两张有多像"，直接写在作业卡上 | "看着像"和"真出了同一张"分不出来。有了度量，用户不必猜，也不必为不是问题的事重跑 |

前端不再自己下载图片：它只调 `GET /api/jobs` 与 `GET /api/job?id=`，落盘完全由服务端完成。页面切到后台（`document.hidden`）时暂停轮询，回到前台立即补拉一次。

**「四张图几乎一样」怎么判断**：批内相似度用的是感知哈希（dHash 64 位），标尺来自本机 40 张真实历史图的实测：

| 对照 | dHash 距离 |
|---|---|
| 同 seed、同参数重跑 | **0** → 逐字节相同，接口确实认 seed |
| 同提示词、不同次生成 | **15 ~ 17** → 构图相近，但确实不是同一张 |
| 不同提示词的随机对照（3907 对） | 中位 **31** |

距离 ≤ 4 才判为"几乎完全相同"并给出警示。也就是说：**同提示词出的几张本来就长得像** —— 那是提示词把构图钉死了（优化器的产物尤其如此），不是种子被复用。真出了同一张，界面会明确写出来。


#### LoRA 适配器

字段名 `loras`，取值是 `{"<仓库 id>": 权重}` 的映射。**这不是摆设**（2026-09 实测）：同一 prompt / size / steps / seed 下，唯一变量是 `loras`，出图逐字节不同 —— 加了 LoRA 的产物 314,148 B，不加 301,292 B，sha256 不同。

| 约束 | 说明 |
|---|---|
| 格式 | `org/name`（ModelScope 仓库 id）。输入框**接受整条社区页面链接**，失焦时自动解析出 id |
| 数量 | 最多 6 个 |
| 权重 | 全部 LoRA 的权重之和必须 **等于 1.0**（容差 0.01），单个权重在 [0, 1] |
| 底座 | LoRA 必须基于同一底座（Qwen-Image-2.1）训练 |

两点必须说清楚：

- **id 写错不是"悄悄不用它"，而是整个请求失败**。接口在提交阶段就会去下载该 LoRA，拉不到时返回 `apiInferModelDownload call failed ... [Model Exception] 模型不存在`。所以前后端都按同一套规则先拦一次（超 6 个 / 非法 id / 权重和不为 1 / 重复 id / 权重越界），而不是等接口报一句看不懂的错。
- **没有"一键载入魔搭 LoRA 列表"这个功能，是因为公开接口做不到**。魔搭的 `/openapi/v1/models` 不需要鉴权，但**所有查询参数都被忽略**（`Name` / `Keyword` / `Query` / `Search` / 分页 / 排序，九种写法返回同一份固定列表，`total_count` 是整站量）；站内搜索接口 `/api/v1/muse/models` 需要登录态（无鉴权 401，带 token 则 500）。因此改为两件离线就能做的事：粘贴链接自动解析，以及「最近用过」（存在浏览器 `localStorage`，最多 8 条，提交成功后自动记录）。

#### 局部重绘（蒙版画笔 / 圈选标注）

选择「局部重绘」后会出现一块画布，上传 1 张原图即可开始标记：

| 控件 | 说明 |
|---|---|
| 画笔 / 橡皮 | 画笔添加标记，橡皮擦掉已画的标记（底层原图不受影响） |
| **自由圈选** | 按住拖拽，自由画一个**封闭的圈**把要改的目标套起来。**不必是圆形** —— 沿物体轮廓随手绕一圈才是它的语义 |
| 矩形框 | 拖拽画一个矩形，适合边缘平直的目标 |
| 笔刷 / 线宽 | **按像素计，最小 1px**、最大 400px，实时显示当前像素值；涂抹与圈选共用同一个线宽 |
| 标记颜色 | **白色**（涂抹掩码用，实测出图最干净）＋ **蓝 / 红 / 绿 / 黄 / 紫 / 青**（圈选标注用） |
| 提交方式 | **涂抹叠加到原图**（单张图，成片最干净）或 **原图 + 独立掩码**（原图不被涂改） |
| 圈选清单 | 把「哪种颜色画了几处」摊开显示，提示词照着它写 |
| 生成指令骨架 | 按已画的颜色插入一段指令模板到提示词里，`___` 处填具体内容 |
| 撤销 / 清空 | 撤销按标记粒度；涂抹与圈选都计入撤销栈 |
| 隐藏标记 | 暂时隐藏标记层以便观察底图，不影响已标记内容 |

##### 这是两种不同的标注方式，官方分开举例

| | 涂抹（painted region） | 圈选（annotations） |
|---|---|---|
| 怎么画 | 画笔涂一块，**单色**（推荐白） | 自由圈选 / 矩形框，**可多色** |
| 颜色含义 | 白色 = 「这里要重画」 | 颜色 = **提示词与画面之间的钥匙**，一色一条指令 |
| 提示词写法 | 指明「白色标记区域」要补什么 | 按颜色逐个说明改什么，末尾声明标注线不要渲染 |
| 提交方式 | 两条都行 | **必须用「涂抹叠加」**（原因见下） |

圈选可以**同时用几种颜色套住几个区域，让模型分别去改**。官方示例就是这么用的：

```
将蓝色圈选区域内的棕色皮表带手表整体移除，并以与手臂肤色一致的皮肤自然延续填补腕部区域；
将红色圈选区域内的蓬松金色头发改为黑色；将两处绿色圈选区域内的白色衣袖换成灰色亚麻睡衣；
蓝色、红色与绿色标注线不得渲染在图像中。
```

三处要点：

- **先说哪个颜色，再说改成什么**。颜色是模型唯一的定位依据，不说颜色它只能猜。
- **同色可以套多处**（官方那句「将**两处**绿色圈选区域内的…」）。所以连续画同一个颜色的多个圈是合法用法 —— 界面只在**从涂抹工具切到圈选工具**时才会自动换色，同一个圈选工具连画几处颜色保持不变。
- **结尾必须声明标注线不要渲染出来**。少了这句，画上去的蓝红绿线会原样留在成片里（官方 FAQ 专门有一条在讲这个）。

##### 两条提交路径对颜色的处理完全不同

- **涂抹叠加**：标记以**各自的不透明色**压在原图上（单张图）。这条路径保留颜色，模型靠颜色分辨各处。
- **独立掩码**：提交 `[原图, 黑白掩码]` 两张，**所有颜色都被抹成白色** —— 掩码只认「白 = 重画」。所以**多色圈选走这条路等于把「一处一改」的意图整段抹平**：钱照样扣，结果却对不上。界面会直接拦下这种组合（改一个下拉即可继续），并且在画布旁常驻提醒。

另外，同一个封闭区域在两条路径上的**画法**也不同：涂抹叠加画成**轮廓**（保留圈线原样），独立掩码自动**填实**成实心区域 —— 掩码里若仍是轮廓，模型只会重画那一圈线本身（甜甜圈），而不是圈内的内容。

##### 界面会替你把关，但绝不替你改提示词

画布下方有一栏**落坑体检**，随提示词实时更新，提交时再提醒一次。三条都是会白花钱的坑：

1. 用了多色圈选却选了「独立掩码」；
2. 提示词里没点名某个颜色（中英文都认）；
3. 少了「标注线不得渲染在图像中」这句。

它只提醒、只拦「表达不出来」的组合，**不会自动修改你写的提示词** —— 提示词是你的东西，悄悄改掉比不改更糟：你会以为发出去的是自己写的那句，历史里存的却是另一段。

##### 三个细节

- **画布分辨率自动对齐接口约束**。上传原图后，画布内部分辨率取原图比例、单边压到 2048 以内、并取 16 的倍数，同时自动填入生成尺寸 —— 这样掩码与请求尺寸严格同尺度，不会因缩放导致重绘区域错位。原图比例过于特殊（取整后偏差 > 5%）时会给出提示。
- **指令里必须指明标记**。模型靠提示词里的描述定位标记区域，例如「把白色标记区域的灌木换成木质长椅」。实测不带标记说明时，模型会把新内容**随机放到画面任意位置**。
- **线宽按像素计，左端就是 1px**。早先按「画布宽度的百分比」取值，于是 1152px 宽的图上最小一档是 12px，粗笔迹涂掩码是省事，但**想顺着物体轮廓描一圈细线就做不到**了。现在线宽是绝对像素，与画布尺寸无关 —— 换张参考图，同一个档位还是同一个像素值（只在**初次**建画布时按宽度 8% 给一个默认值，你一动手调过就再也不会被重置）。因为 1–400px 的跨度摆不进一条线性滑块（那样 1/2/3/4px 会全挤在一个屏幕像素里，恰恰是描轮廓最常用的几档），滑块走的是**对数档位**：0–25 档细分成 1–4px，50 档约 20px，100 档 400px。另外**屏幕预览会按缩放比给细线一个约 1.2 CSS 像素的可视下限**（1152px 的画布摆在 640px 宽的框里，1px 的线缩下来只剩 0.5px，再叠上预览透明度就基本看不见了，会被误当成"没画上"）；**导出严格按设定像素走**，屏幕上看着略粗、成片里是细线。

> **已知缺口：优化器的官方 edit 规范不认识「圈选」**。该规范里有一条 *"do not clean up unmentioned defects, overlays or clutter"* —— 标注线恰好属于 `overlays`，也就是说送去优化时，模型可能反过来**要求保留**标注线，并把「标注线不得渲染」这句当成多余信息丢掉。目前项目**没有**为圈选另立附加规则文件（`data/rules/extra_transparent_subject.md` 只管透明与抠图两件事），所以圈选提示词建议**直接手写**，或优化后再人工确认两个要点：颜色逐个点名、结尾的排除句还在。


### 提示词优化（Chat）

**第一件事是选类型**，而不是先打字。类型决定这次用哪份官方规范，两者产出完全不同：

| 类型 | 使用的规范 | 产出长相 |
|---|---|---|
| **文生图提示词** | `official_t2i.md`（Image Prompt Rewriting Expert） | 一段约 400–500 词的英文观察式描述，附 `wh_ratio` |
| **编辑图片提示词** | `official_edit.md`（Edit Prompt Enhancer v2） | 一段编辑指令，描述语言随你的指令语言；附 `wh_ratio` 或 `ratio_follow` |

类型是**对话的属性**，存在对话本身里：在改图模式下聊文生图提示词，用的仍然是文生图规范。

> ⚠️ 类型**不**跟创作台的模式联动。早期版本按创作台模式推断类型，导致「在图像编辑模式下聊文生图提示词」被套上编辑规范，产出的东西和预期完全对不上 —— 这是本项目踩过的一个真实坑。

每个对话顶部会显示「累积轮次数」，右侧列表里可以：

- **新建对话** —— 开一个干净上下文的新对话（沿用当前类型）
- **重命名** —— 手动改标题；不手动改时，首次发消息会按你的需求自动命名
- **删除** —— 连同其中的消息一起删除（会二次确认）
- **切换类型** —— 换规范后会明确告知有多少条旧类型的消息不再参与上下文

多轮迭代时，只有**与当前类型相同**的消息会作为上下文发给模型，所以同一个对话里先后做过两类提示词也不会互相污染。若某轮请求还没返回你就切走了对话，结果仍会保存回它原本所属的对话。

**右侧「当前使用的规范」卡片会亮出真实文件指纹**（文件名 / 字节数 / 行数 / sha256 前 12 位 / 章节大纲），点「查看规范原文」可以直接读模型收到的规范全文。规范文件换成什么，这里就显示什么 —— 用来回答「应用到底在用哪份规范」这个疑问。开了附加规则时，卡片里会多一段附加规则的文件与指纹，并可单独点「查看附加规则原文」。

#### 附加规则（可选，默认关闭）

两份**官方规范都没有覆盖**两件事：透明图句式、主体提取。补这两块有两种做法 —— 往官方规范里加内容，或者另立一份补充条款。本项目选后者：

- `data/rules/extra_transparent_subject.md` 是**项目自写**的补充条款，**不是**官方规范，也不改动官方文件一个字节。
- 勾选对话头部的「附加规则」后，它作为**独立的第二条 system 消息**追加发送：`messages[0]` 仍是官方规范原文（逐字节相同），`messages[1]` 是附加规则原文。不勾选时，请求与加这个功能之前完全一致。
- 开关是**对话级**设置，随对话保存：做抠图的对话开着，做普通海报的对话关着，互不影响。
- 附加规则缺失时开关会被禁用并说明原因；已勾选却读不到文件时，接口如实返回 500 而不是悄悄降级成"只用官方规范"。

它写的是什么（都是贴合官方模型卡原话的规则，不是自由发挥）：

| 规则 | 要点 |
|---|---|
| 透明图（RGBA） | 逐字使用模型卡给的固定句式：`This is an RGBA image with transparency. <画面描述>. The image has alpha channel and the background is transparent.`；中间那句必须是完整句；不得用「白底 / 无缝背景 / 影棚」等**不透明**说法替代；不用质量词、不在句外出现 RGBA/位深等术语 |
| 主体提取（抠图） | 明确"只输出孤立主体、原背景完全移除"；按画面里真实存在的样子命名主体（不得编造）；保持原始比例、姿态、视角与打光；指明边缘处理（无光晕、无残留背景色溢出）；发丝 / 镜框 / 细带等细结构必须保真；编辑任务仍用 `<imageN>` 引用并要求跟随原图比例 |
| 句式位置 | t2i：首句之前放第一句固定句式、收尾句之后放第二句，官方要求的句数与词数不变；edit：单段密集段落的首尾各放一句，`<imageN>` 与比例字段规则不变 |

> 一句话总结：**官方规范动不了，缺的那两块单独成文件，要用才勾。** 界面上「查看规范原文」与「查看附加规则原文」是两个按钮，就是为了让这件事一眼可辨。

### 锁定图片：让模型真正"看见"画面

编辑规范要求「每一个空间、色调、语境的判断都来自画面里实际存在的东西」。也就是说 **优化器必须能看到图**，否则只能写笼统的保留声明。

对话里有一个「锁定图片」区（在类型选择下方），锁定的图会在每次改写时真正**随消息发给模型**：

- **从创作台带入** —— 把创作台已上传的参考图压缩后锁定过来（创作台的「去优化提示词」按钮在跳转时也会**先询问**是否带入，不会替你决定）
- **上传** —— 直接在对话页选图，不必回创作台
- **逐张移除 / 清空** —— 只影响锁定关系，不影响对话记录与已产出的提示词

最多锁 6 张（模型侧的成本与响应时间考虑），超出会明确告知。

> **「锁定」是真的锁定**：图片随对话一起持久化，之后在创作台换图、删图都不影响这个对话。

锁定的图**压缩后落盘到 `inputs/`**，对话记录里只存文件名引用。这样 `data/conversations.json` 不会被几 MB 的 base64 撑大（实测一次迁移让该文件从 27 万字节降到 7.8 KB），图片也可以直接打开查看。发给模型时由服务端按对话读盘组装，前端不再随请求重复带一份 base64 —— 两边各持一份只会带来「界面显示有图、模型收到的是另一张」这类难查的分裂。

两条路径的压缩规格不同，因为目标不同：

| | 交给谁 | 规格 |
|---|---|---|
| 创作台参考图 | 生图模型（要求画质） | 仅在超限时压到单边 2048 / JPEG 0.92 |
| 锁定图 | 视觉模型（只需看懂内容） | 单边 1024 / JPEG 0.82，通常 100KB 上下 |

带透明通道的 PNG 素材**不会**被转成 JPEG —— 会先抽样探测是否**真有透明区域**，有才继续输出 PNG，避免把抠好的素材压成黑底。

> 判据是「明显透明的像素占比 > 1%」，而**不是**「存在 alpha < 250 的像素」。模型产出的 RGBA PNG 在柔边与抗锯齿处普遍带 alpha 239~254 的值，视觉上完全不透明；早期按 250 判定会把它们统统判成透明图，于是保住 PNG 不走 JPEG，同一张图从 86 KB 涨到 955 KB，直接超出服务端单张上限被丢弃 —— 界面上同时弹出「已锁定 1 张」和「服务端只接受了 0 张」，自相矛盾。

> 落盘解决的是**存储**问题，不是**体积**问题：这些图最终仍要以 base64 送进视觉模型，所以单张体积上限依旧与服务端一致。前端在压缩时就按这个上限收敛（并有一道兜底：任何分支产出超限都会继续缩尺寸，绝不把超限的图交出去）。

**没给图却要求改图时会主动提醒**：打字过程中若识别出"把这张图改成…"这类编辑意图而对话里没有图，提示条会给出引导；发送时还会确认一次，避免你拿到一份盲写的编辑指令却以为模型看过图了。

提示的时机是克制的：**空对话、空输入时不显示任何提示**（早期版本每次渲染都弹，很吵，已修正），只有你正在写东西时才出现。

> 此功能会调用大模型，**必须先配置 API Key**。

### 生图历史（History）

按时间倒序展示全部产出，每张卡片显示缩略图、提示词与参数标签（尺寸 / 步数 / cfg / seed / 格式），支持下载、复制提示词、删除。

若某条记录对应的图片文件已不在 `outputs/` 中，卡片会显示「图片文件已丢失」占位块并**禁用下载**，但**提示词与参数仍完整保留**（详见[数据与安全](#数据与安全)）。

### 个人信息（Profile）

API Key 的填写、校验、清除与余额查询，以及优化器引擎配置。Key 在界面上始终以掩码形式回显（仅显示前 6 位与后 4 位）。

## 尺寸预设

界面上可选的 10 个尺寸，全部满足「单边 ≤ 2048 且为 16 的倍数」：

| 比例 | 尺寸 | 比例 | 尺寸 |
|---|---|---|---|
| 1:1 | 1024 × 1024 | 2K 1:1 | 2048 × 2048 |
| 2:3 竖版 | 1024 × 1536 | 2K 2:3 竖版 | 1360 × 2048 |
| 3:2 横版 | 1536 × 1024 | 2K 3:2 横版 | 2048 × 1360 |
| 16:9 宽屏 | 1536 × 864 | 2K 16:9 | 2048 × 1152 |
| 9:16 手机 | 864 × 1536 | 2K 9:16 手机 | 1152 × 2048 |

> 常见的 **2048 × 3072 是非法的** —— 单边 3072 已超过 2048 上限，会被接口拒绝。想要更大画幅需在出图后另行超分。
>
> **官方模型卡给的 2K 宽高比经此 API 全部不可达**。模型卡列的是 `4:3 → 2400×1792`、`3:2 → 2528×1696`、`16:9 → 2752×1536`、`9:16 → 1536×2752`，长边都超过 2048，实测直接返回 `width must be integer in [64,2048]`；只有 `1:1 → 2048×2048` 能用。上表的「2K」档因此是**在单边 2048 的约束下尽量贴近**对应比例（比例会有不到 1% 的偏差，若追求整数比例请用 1K 档）。要拿到官方那些尺寸只能本地跑 diffusers 管线。

## 谁决定输出尺寸：提示词里的比例，还是页面的尺寸参数？

**页面参数。** 提示词**从不**被解析成尺寸 —— `size` 永远只来自界面上的「尺寸预设 / 自定义宽高」。

实测方式：把 `MS_BASE` 指向本地假接口启动真实服务端，截获**实际发出去的请求体**（16 项断言全通）。请求体字段集恒为 `model, prompt, size, image_url` —— **没有任何"跟随输入图"或"从提示词推断比例"的字段**。

| 提示词里写 | 页面尺寸选 | 实际发出的 `size` | 提示词文本 |
|---|---|---|---|
| `...framed in 2:3 at 2048x3072...` | 1:1 1024×1024 | `1024x1024` | 原样保留（含 `2:3`、`2048x3072`） |
| 官方 JSON 外壳 `wh_ratio: "2:3"` | 16:9 1536×864 | `1536x864` | 剥壳后只剩正文，备注提示壳内比例 |
| 未写比例 | 未选尺寸 | **不发送** `size`（接口退回默认 760×1280） | — |
| `...a cinematic 16:9 frame at 2K...` | 自定义 1360×2048 | `1360x2048` | 原样保留 |

所以**冲突既不报错也不自动纠正**：画布被页面参数钉死，而提示词里的比例/横竖描述会被扩散模型当**内容**读进去。两者不一致时表现为「构图被硬塞进另一个画幅」（大面积留白、主体挤到一侧、类似加了信箱边框），而不是弹错误。

### 但正常流程里撞不上

优化器返回 `wh_ratio` 时，前端会**自动把它同步到尺寸控件**（`applyRatio()`）：命中内置预设就直接选中，没有对应预设则按 1024 基准算自定义宽高。

| 返回的 `wh_ratio` | 同步结果 |
|---|---|
| `2:3` | 选中预设「2:3 竖版 1024×1536」 |
| `9:16` | 选中预设「9:16 手机 864×1536」 |
| `18:39`（无预设） | 自定义 `944×2048`（16 的倍数且夹在 `[64,2048]`） |

**只有两种情况会真撞上：**

1. 填入优化结果后**又手动改了比例**（结果说 2:3，你把下拉拨到 16:9）
2. **自己手写/粘贴提示词**并带比例字样 —— 这条路径不经过 `applyRatio()`，比例不会被同步，也**不像优化器输出那样被清洗**

也就是说：**优化结果的正文里不会有数字比例**（解析时清洗掉 `2:3`、`1920×1080`、`2K` 这类字样，规范也明令禁止写进正文），只留一个**方向形容词**（`vertical` / `wide` / `square`）。手写提示词没有这层保护。

### 图片编辑 / 局部重绘：跟随原图，还是跟随页面？

接口层面**没有**「跟随输入图尺寸」这个概念（上面字段集已证明）。是否跟随原图，**完全由提交那一刻界面上显示的数字决定**。两种模式的默认行为不同：

| 模式 | 上传原图时对尺寸的处理 |
|---|---|
| **局部重绘 (inpaint)** | **自动把自定义宽高对齐到原图尺寸**（夹到 16 的倍数、单边 ≤2048）；取整后比例偏差 >5% 时提示「可能有轻微形变」。注释写明「否则重绘结果会被拉变形」 |
| **图片编辑 (edit)** | **不对齐** —— 尺寸保持你上次选的值（默认 `1:1 1024×1024`），想跟随原图需**手动**改 |
| **图生图 (i2i)** | 同 edit，不对齐 |

> ⚠️ **已知缺口**：编辑规范的 `ratio_follow: "<image1>"` 语义是「输出跟随第 1 张输入图的尺寸」，是规范要求**调用方去执行的尺寸决策**。目前本项目只**消费** `wh_ratio`（→ 自动设尺寸），对 `ratio_follow` **仅在界面上显示「跟随 <image1>」标签，不会改尺寸**。模型回 `ratio_follow` 时，需要你自己把尺寸调成原图比例。见[已知限制](#已知限制)。

## 实测得出的 API 约束

这部分是本项目踩坑后固化的结论，**与官方文档存在出入**，按实测为准。

> **这个接口对未知参数一律静默忽略**：返回 200、任务 SUCCEED、不报错、不打日志，参数就是不生效。下面「字段名」一列的大部分结论，都是用一个**越界值**去打接口得出的 —— 报校验错误说明字段被识别，返回 200 说明字段根本不存在。

### 字段名与取值范围

| 参数 | 官方文档说法 | 实测结论 |
|---|---|---|
| **输入图字段名** | 未明确区分 | ⚠️ **必须是 `image_url`（单数）**。写成 `image`、`image_urls` 或 `images` 会被**静默忽略** —— 接口返回 200、任务 SUCCEED，但参考图从未参与，出图完全由提示词决定 |
| `image_url` 取值 | — | 接受 **data URI**（`data:image/png;base64,...`），也接受**数组**（用于「原图 + 掩码」两图输入） |
| **`image_url` 张数** | 「最多 10 张参考图」 | ⚠️ **经此 API 最多 4 张**。第 5 张起**提交阶段直接 400**：`image_url count 5 exceeds maximum limit of 4`。外链 URL 同样按张数计数拦截，换字段名也绕不过去（见下方「关于 10 张参考图」） |
| **采样步数** | — | ⚠️ 字段名是 **`steps`**，范围 **[1, 50]**。写成 `num_inference_steps` 会被**静默忽略**（滑块会变成摆设） |
| **引导系数** | — | ⚠️ 字段名是 **`guidance`**，范围 **[1.0, 20.0]**。写成 `guidance_scale` 会被**静默忽略**。`guidance ≤ 1` 时 `negative_prompt` 的负向分支失效 |
| `seed` | `[0, 2^31-1]` | 实测 **`[-1, 2147483647]`**，`-1` 即随机；越界返回 `seed must be in [-1, 2147483647]` |
| `prompt` 长度 | 2000 字符 | **实际可到 4000 字符**。本项目以 4000 为硬上限，3200 为安全目标（超出会自动追加压缩指令重试一次） |
| 尺寸传参 | `width` / `height` | **只认 `size: "WxH"` 字符串**。传 `width`/`height` 会被**静默忽略**，模型退回默认纵向比例 **760 × 1280**，且不报错 |
| 尺寸范围 | — | 单边 **64 ~ 2048**（是单边上限，**不是总像素上限**），且必须为 **16 的倍数**。**不需要 32 对齐** —— `1360×2048` 实测原样接受 |
| **`loras`** | 可选，最多 6 个、权重和 1.0 | ✅ **真实生效**。格式 `{"<仓库 id>": 权重}`（单条也可写字符串）。实测：不存在的仓库 id 会让接口在提交阶段就去下载并返回 `apiInferModelDownload call failed ... [Model Exception] 模型不存在`；同 seed 对照下加与不加出图逐字节不同 |
| **`prompt_extend`** | — | ✗ **不被识别** —— 这其实是好事：接口不会二次扩写、覆盖掉优化器产出的提示词 |
| **`cfg_scale` / `true_cfg_scale`** | — | ✗ 都不被识别。那是 DiffSynth 本地管线的参数名，不适用于本接口 |
| **`watermark`** | — | ✗ **不被识别**。接口没有水印开关（界面上曾有这个复选框，已移除） |
| **输出格式** | — | ✗ **没有这个参数**（`output_format` / `outputFormat` 都不被识别）。模型 VAE 工作在 4 通道 RGBA 空间，**每张图都是 RGBA 容器**；画面是否真的透明**完全由提示词决定**，见下方「透明背景」 |
| 局部重绘掩码 | 涂抹 / 自由圈选 / 矩形框 / 独立掩码 | 都能用，但**掩码是必要条件**。对照实验中不带掩码时，模型会把新增内容随机放到画面任意位置；带掩码才精确落在标记区域。涂抹用**白色**标注实测比红色更干净。**彩色圈选是另一条路**：它靠颜色与提示词对号入座，且只能走「涂抹叠加」——「独立掩码」会把所有颜色抹成白色 |
| 任务模式 | — | 两段式异步：`POST /v1/images/generations` 拿 `task_id`，再轮询任务状态取结果 URL |

因为「传错参数不报错、只是悄悄换尺寸」，服务端会在保存图片时**读取 PNG 真实像素**并与请求值比对，不一致就在历史里标记，避免你以为出了 2K 图、实际拿到 760×1280。同理，越界参数会被钳制、超量参考图会被截断，两种情况都会在提交后**当场提示**，不让参数无声无息地失效。

> `image` vs `image_url` 这个坑值得单独强调：它不会报错、不会有任何日志，唯一的迹象是**出图与输入图毫无关系**。`num_inference_steps` / `guidance_scale` 属于同一类坑 —— 界面上有旋钮、拖动有反馈、提交不报错，只是模型完全不知道你调过。如果你在别的 ModelScope 项目里也遇到「参数/参考图不生效」，先检查字段名。

### 透明背景（RGBA）

**接口没有输出格式参数**，模型恒输出 RGBA 容器 —— 容器里有 alpha 通道，但画面大概率是全不透明的。官方模型卡对此给了一段固定句式，必须写进提示词才能得到真正透明的背景：

```
This is an RGBA image with transparency. <你的画面描述>
The image has alpha channel and the background is transparent.
```

创作台选择「透明背景」后，服务端会检测提示词里是否已表达透明意图，没有就按上述句式自动补齐（已表达则不重复拼）。补齐时会顺手补一个句号：模型卡示例里中间那句是**完整句**，而手写的中文需求常常没有句号，直接拼会把两句连成一句。

> 想自己判断一张图到底有没有真透明，看 alpha 通道的实际分布，不要看容器格式 —— 本项目所有历史图的 `colorType` 都是 6（RGBA），但绝大多数画面在视觉上完全不透明。实测：不勾透明背景时产物 `<32` 透明像素占比约 0%，写了固定句式后可达 47.6%。

**这条路径只解决"生成时的提示词"。** 如果你要的是「提示词优化器**改写出来**的提示词本身就带透明句式」，那属于两份官方规范都没覆盖的领域 —— 见[附加规则](#附加规则可选默认关闭)（勾选后优化器也会写出透明图句式）。

## 提示词优化

核心思路：**不自己造规则，直接把官方规范原文当 system prompt 喂给模型。**

- `data/rules/official_t2i.md` → 文生图规范（Image Prompt Rewriting Expert，8 个步骤）
- `data/rules/official_edit.md` → 图像编辑规范（Edit Prompt Enhancer v2）
- `data/rules/extra_transparent_subject.md` → **附加规则（项目自写，非官方）**，只有勾选时才作为第二条 system 消息追加

后端 `readRule()` 读取文件内容，作为 `system` 消息发出，不做任何转述或摘要 —— 转述必然引入偏差。

### 规范文件是唯一事实来源

界面上展示的规范信息（文件名 / 字节数 / 行数 / sha256 前 12 位 / 章节大纲）全部由 `/api/rules` 从真实文件现场提取，**没有任何手写摘要**。早期版本右侧栏有一份手写的「提示词结构模板 / 官方要点」，它随规范漂移，甚至写着与规范相反的劝告（鼓励 `highly detailed, photorealistic`，而 t2i 规范明令禁止质量词）。那部分内容已删除。

`readRule()` 的缓存按 `mtime + size` 失效，**替换规范文件后无需重启服务即可生效**。

### 类型必须显式指定

`/api/optimize` 的 `kind` 由前端根据**当前对话的类型**提交，服务端也不会从「有没有传图片」去反推。理由是编辑规范与文生图规范对同一句话的产出完全不同，任何隐式推断都会在某些使用姿势下选错规范。

另一个容易漏的点：**t2i 规范只定义 `rewritten_prompt` 与 `wh_ratio` 两个字段**，没有「跟随某张输入图」的概念。服务端在 `kind === 't2i'` 时会强制清空 `ratio_follow`，避免模型多吐的字段污染下游尺寸设置。

### 输出解析：「官方 JSON」是模型输出格式，不是提示词本身

两份规范都**明文要求模型按 JSON 回复**：

- t2i：`Return one strictly valid JSON object on a single line, nothing before or after`
- edit：`Output a valid JSON object with exactly three fields` / `Do not include any text outside the JSON object`

所以要分清**三个位置**，各自的正确形态并不相同：

| 位置 | 正确形态 |
|---|---|
| **模型 → 程序**（模型的回复） | **必须带壳**：`{"rewritten_prompt": …, "wh_ratio": …}` |
| **壳里的 `rewritten_prompt`** | **纯自然语言描述**，不带任何 JSON 符号 |
| **程序 → 生图接口的 `prompt`** | **必须不带壳**（该字段是字符串，比例走独立的 `size` 参数） |

也就是说，「带壳」本身不算错，**错的是位置**。本项目据此分工：发给模型的规范一字不改、模型照规范吐 JSON；解析层负责把正文取出来，用于展示与生图。

解析是**五级兜底**：剥离 markdown 围栏 → 直接解析 → 提取最外层 `{...}` → 修复字符串内未转义的换行 → 正则抽取字段。拿到后按规范清洗正文：去换行、去混入的比例/分辨率、去质量词。

**结果卡片给两种形态**：

- **「复制正文」** —— 纯提示词，可直接拿去生图
- **「官方 JSON」** —— 按官方契约重建的完整 JSON（t2i 两字段 / edit 三字段），用于存档、迁移、喂回模型

**反向保护**：如果直接把带壳 JSON 粘进创作台的提示词框，服务端会在提交前**自动剥壳**并在备注里说明 —— 否则 JSON 标点会作为提示词进画面，壳里的 `wh_ratio` 还会顶撞 edit 规范「正文不得出现比例」那一条。只有确实长得像官方契约的输入才会被剥，普通正文一律原样送出。

### 视觉输入：把图真正递给模型

请求里**不需要**传图片。前端只提交 `convId`，服务端按该对话从 `inputs/` 读盘、组装 dataURL，再按 OpenAI 兼容的多模态格式随 user 消息发出：

```json
{ "role": "user", "content": [
  { "type": "text", "text": "【本次输入图片数量：1 张，已随本条消息附在下方…】\n\n用户指令：…" },
  { "type": "image_url", "image_url": { "url": "data:image/jpeg;base64,…" } }
] }
```

编辑类型会明确图片数量与 `<imageN>` 的对应顺序；文生图类型声明"附图仅作风格参照，正文不要出现引用标签"（t2i 规范没有 `<imageN>` 概念）。

**为什么这件事是必须的** —— 同一句需求「把旗袍的颜色改成酒红色，其他保持不变」的实测对照：

| | 附图 | 不附图 |
|---|---|---|
| 产出的提示词引用到的画面元素 | 11 个（金色提花、盘扣、立领、帆布包、高跟鞋、盲道砖、列车、站台立柱…） | 2 个（盘扣、开衩 —— 靠"旗袍"常识猜的） |
| 保留声明的具体程度 | 「左侧贴着浅灰瓷砖的立柱」「短款黑色波波头」「暖调阳光」 | 「保持背景、构图、镜头视角、景深…」 |

模型只要真正看到画面，产出就从"笼统保留"变成"逐项精确保留"。

**不需要换模型**：默认使用的 `deepseek-ai/DeepSeek-V4.1-Flash` 本身就具备视觉能力（实测能准确说出服装形制、手中物品、环境光线方向）。早前 README 里"要彻底解决需换成支持视觉的模型"是**未经实测的推测**，现已推翻。

<details>
<summary>踩过的坑：极小的测试图会让模型"看不见"</summary>

用 1×1 或几百字节的纯色小图做探测时，服务端会把它降级/丢弃，模型只能靠猜（实测 DeepSeek 在这类输入下的推理过程里写着"打开图片？我不能"，猜的色值和真实色值差很远）。换用真实的 1.8MB 生成图后表现完全正常。

**结论：验证视觉能力必须用真实尺寸的图片，不能用占位小图**，否则会得出"模型不支持视觉"的错误结论。同一个端点下，`OpenGVLab/InternVL3_5-241B-A28B`、`PaddlePaddle/ERNIE-4.5-VL-28B-A3B-PT` 虽然名字带 VL，但返回 `choices: null` 的空壳响应，实际不可用 —— 名字不能当证据。

</details>

### 图片数量与体积上限

| 限制 | 值 | 超出时 |
|---|---|---|
| 单次送入模型的图片数 | 6 | 按顺序取前 6 张，响应里报告丢弃张数 |
| 单张 dataURL 长度 | 900,000 字符（约 670KB） | 丢弃该张 |
| 单次图片总长度 | 4,000,000 字符 | 丢弃该张 |
| 单个对话可锁定数 | 6 | 界面拦下并提示 |

只接受 PNG / JPEG / WebP 的 dataURL，校验用前缀 + 首尾抽样（不对近 MB 的字符串做全量正则，避免回溯）。

### 输出为空时的兜底

推理模型会把输出预算花在思维链上。若首轮 `content` 为空而 `reasoning_content` 非空，说明预算被推理占满，服务端会**加大预算重试一次**；仍为空则给出明确错误，而不是含糊的「优化结果为空」。带图请求的输出预算高于纯文本（6000 vs 4000），因为思维链更长。

### 历史消息会带回模型

多轮迭代时，历史里的 assistant 消息按规范要求的 JSON 形态回灌（t2i 两个字段，edit 三个字段），让模型理解上一版结果。同一对话内只有与本轮类型一致的消息会参与上下文。

## HTTP 接口

后端所有接口都在同一个端口下：

| 方法 | 路径 | 说明 |
|---|---|---|
| `GET` | `/` | 前端页面（以及 `/app.js`、`/style.css`） |
| `GET` | `/outputs/*` | 已生成的图片 |
| `GET` | `/inputs/*` | 对话锁定的参考图（落盘的压缩图） |
| `GET` | `/api/config` | 读取配置（Key 以掩码返回，**不回传明文**） |
| `POST` | `/api/config` | 保存 Key 与优化器配置 |
| `POST` | `/api/verify` | 校验 Key 是否可用 |
| `GET` | `/api/balance` | 查询魔豆余额 |
| `POST` | `/api/generate` | **创建生成作业**（不再是同步单张提交）。一次可含 1–4 张，返回 `jobId`、`items`（含每张自己的 `seed`）、**实际发出的参数 `sent`** 与调整说明 `note`。运行中的作业堆到上限（默认 5）才返回 **409**，且不发任何上游请求 |
| `GET` | `/api/job?id=` | 查询单个作业（状态、每张的进度 / 文件名 / 失败原因），未知 id 返回 404 |
| `GET` | `/api/jobs` | 最近 10 个作业 + 当前进行中作业的 `activeId`。页面加载时用它发现"上次那个还在跑"从而重连 |
| `POST` | `/api/job/cancel` | 停止跟踪某个作业，body `{id}`。**只停止轮询**，已提交给上游的任务仍在执行，额度不退 |
| `GET` | `/api/task?id=` | 直接向上游查询任务状态（旧接口，保留兼容；前端已不再使用） |
| `POST` | `/api/save` | 下载结果图片落盘并写入历史（旧接口，前端已不再调用；作业会在服务端自动落盘） |
| `GET` | `/api/history` | 读取历史列表 |
| `DELETE` | `/api/history/:id` | 删除某条记录（可选是否连图片一起删） |
| `POST` | `/api/optimize` | 提示词优化（`kind` 必填；`convId` 指定用哪个对话锁定的图） |
| `GET` | `/api/rules` | 规范文件元信息（文件名 / 大小 / 行数 / sha256 / 章节大纲） |
| `GET` | `/api/rules/:kind/source` | 规范原文（`kind` = `t2i` / `edit`） |
| `GET` | `/api/conversations` | 对话列表与当前对话（图片为文件名引用，不含 base64） |
| `GET` | `/api/conversations/:id` | 单个对话完整内容 |
| `POST` | `/api/conversations` | 新建对话，body `{kind, title?, images?}` |
| `PATCH` | `/api/conversations/:id` | 更新对话（`title` / `kind` / `messages` / `images`） |
| `DELETE` | `/api/conversations/:id` | 删除对话 |
| `POST` | `/api/conversations/active` | 切换当前对话，body `{id}` |

`images` 每项支持两种形态：`{name, dataUrl, w, h}` 表示一张新图（服务端写入 `inputs/` 并替换为引用），`{name, file, w, h}` 表示沿用既有引用（不重写文件）。响应里的 `images` 一律是引用形态 `{name, file, w, h, bytes}`。

`/api/optimize` 只认 `convId`：

- `convId: "c_xxx"` —— 服务端从该对话读取已锁定的图，再从 `inputs/` 读文件组装 dataURL

早期还允许前端直接用 `imageData` 提交 base64，现已移除。两条路并存意味着同一组图有两个真相来源，一旦前端内存里的图与实际落盘的文件不一致，就会出现"界面显示有图、模型收到的却是另一张（或什么都没有）"——这类分裂极难排查，不如只留一条路。

响应里会回传 `visionUsed` / `visionImageCount` / `visionNote`，用来确认"这次到底有没有把图送给模型"——带了图却没生效时前端会直接报错，而不是让你误以为模型看过图。

请求体上限 60 MB（`/api/generate` 的参考图以 dataURL 提交，需要较大余量）。静态文件服务做了路径穿越防护：`/outputs/` 与 `/inputs/` 一律只取 `path.basename`，丢掉任何目录成分。

## 数据与安全

- **API Key 只存在本地** —— 存于 `data/config.json`，不会发往除你配置的 API 端点之外的任何地方。接口回传时一律掩码。
- **`data/config.json` 已被 `.gitignore` 忽略**，且有 `config.example.json` 模板。提交前建议再 `git status` 确认一次。
- **历史元数据永不自动删除** —— 历史记录里的提示词、参数、种子是不可再生的，图片丢了还能重出，参数丢了就永远没了。因此 `GET /api/history` 只**标记** `missing: true`，绝不剪枝；删除一律走 `DELETE` 显式操作。
- **覆盖写前自动备份** —— 历史文件每次写盘前会先留一份 `history.bak.json`，任何误写都能回退一步。
- **作业队列只存参数，不存图片** —— `data/jobs.json` 记录每个作业的参数与上游任务 id（用于重启后继续轮询），保留最近 30 个。图片本体落在 `outputs/`，元数据落在 `history.json`，三者不重复存。
  - **`jobs.json` 里没有 API Key**。作业对象在内存里带一把提交时用的 Key（后台轮询必须与提交用同一把），落盘时显式摘掉 —— 密钥不进文件，也就不会随备份或误提交外泄。
- **提示词对话同理** —— `data/conversations.json` 记录你手写的需求与模型产出的提示词（同样不可再生），每次覆盖写前留一份 `conversations.bak.json`；已被 `.gitignore` 忽略。单个对话保留最近 200 条消息、最多 6 张锁定图，总对话数上限 80（超出时优先丢弃最旧的空对话）。
- **锁定的图片落盘到 `inputs/`，对话记录只存文件名** —— 这是"锁定"能成立的前提（创作台换图不影响已锁定的对话），同时避免 `conversations.json` 被 base64 撑大。`inputs/` 同样被 `.gitignore` 忽略，服务启动时自动创建。
  - 一个附带好处：**出问题时可以直接打开 `inputs/` 里那张图**，确认"模型看到的到底是哪张、压缩后是什么样"，不必再从 JSON 里挖 base64。
  - 旧的「base64 直接存进对话」的数据会在**首次启动时自动迁移**到 `inputs/`，不会丢图。
  - 文件回收：整组替换锁定图、清空锁定图、删除对话时即时删除对应文件；启动时再清理一次无人引用的孤儿文件（保留 10 分钟宽限，避免误删正在写入的文件）。
- 服务默认只监听本机。**不要直接暴露到公网** —— 它没有鉴权层，任何能访问端口的人都能拿到你的 Key 状态并消耗你的额度。

## 常见问题

**运行 `python server.js` 报 `SyntaxError: invalid character '—'`？**
用错解释器了。这是 Node.js 项目，请执行 `node server.js`。

**出图尺寸和请求的不一致？**
参见[实测约束](#实测得出的-api-约束)：`width`/`height` 会被静默忽略。用界面上的预设即可，它们都是合法值。

**提示词优化报「需要调用大模型，请先填写 API Key」？**
优化功能必须走大模型，请配置 Key（或把 `optimizer.baseUrl` 指向本地模型服务）。出图则仅依赖顶层 `apiKey`。

**优化失败，报 `getaddrinfo ENOTFOUND api-inference.modelscope.cn`？**
这是**本机 DNS 解析**问题，与 API Key、模型名无关 —— 该域名在公网上一直存在（A 记录 `39.99.133.195` / `47.92.141.220`，与主站 `modelscope.cn` 同 IP）。最常见的诱因是系统 DNS 指向本地代理工具（Clash 一类），其解析器偶发失效、负缓存未过期，或**规则集里没有这个域名**。

先看清楚一个反直觉的现象：**浏览器能打开魔搭，不代表这个域名能解析。** 浏览器的解析通道和 Node 不是一条（自带 DoH / 走代理链路）。实测过更极端的情况 —— 同一个解析器对 `www.modelscope.cn` 解析得好好的，却**只对 `api-inference.modelscope.cn` 稳定返回 NXDOMAIN**，重试 3 次全败。所以「浏览器能开」不能用来排除 DNS 问题。

**2026-09-26 起，应用会自己救回来。** 所有出站请求都挂了一个自定义解析器：

1. **先走系统解析器** —— 你的 `hosts`、内网 DNS、代理工具的解析意图优先，绝不抢跑；
2. **只有它失败时**，才用**独立的** c-ares resolver 直接问公共 DNS（默认 `119.29.29.29` / `1.1.1.1` / `223.5.5.5`，可用 `MSQ_DNS_FALLBACK` 改或关）。

只替换「域名 → IP」这一步：URL、Host 头、TLS SNI 全部保持原样，所以证书仍按域名校验，不会因为直连 IP 而失效。触发时服务端会留一行日志：

```
[net] 本机解析器无法解析 api-inference.modelscope.cn（ENOTFOUND），
      已改用公共 DNS（119.29.29.29 / 1.1.1.1 / 223.5.5.5）解析为 39.99.133.195, 47.92.141.220。
      建议检查本机 DNS / 代理工具设置；如需关闭兜底请设 MSQ_DNS_FALLBACK=off
```

所以正常情况下你**什么都不需要做**。

⚠️ 一个必须说清的权衡：兜底走的是**直连**，不经过你的代理隧道。它**只在系统解析器已经失败时**才触发（那时那条路本来就不通），但如果你需要靠代理隐藏来源，这个兜底会绕开它。那种情况下请设 `MSQ_DNS_FALLBACK=off`，然后去修本机 DNS。

如果**开了兜底仍然**报解析失败，那就不是本机 DNS 的毛病 —— 错误提示会明确说「本机解析器与公共 DNS 都解析不出来」，并让你确认网络连通，而不是让你去重启代理（重启也没用）。

仍然想根治本机环境（可选）：

1. 看能否解析（Node 走系统解析器，比 `nslookup` 准）：
   `node -e "require('dns').lookup('api-inference.modelscope.cn',(e,a)=>console.log(e||a))"`
2. 用公共 DNS 对照，确认域名本身没问题：
   `nslookup api-inference.modelscope.cn 223.5.5.5`
3. 重启代理 / DNS 工具，或等几十秒（瞬时故障会自愈）
4. 长期不稳定可在 `hosts` 里固定：`39.99.133.195 api-inference.modelscope.cn`

另外应用对**连接级**失败还会自动重试 2 次 —— 但只重试"同一条路"的错误。**解析双路都失败时不会重试**（同一个名字再问一次不可能突然通，每次兜底最长要等 4 秒，重试 3 轮就是十几秒白等）。请求未送达服务端，所以重试不会重复计费。

> 注意：此处的报错文案曾经**无差别**追加「需要可用的 API Key」，使网络故障被误判成 Key 问题。现已按真实原因分类（网络 / 鉴权 / 限流 / 服务端各给对应提示）。

**查余额 / 校验 Key 报 `getaddrinfo ENOTFOUND modelscope.cn`？**
和上一条同源，但域名不同：余额与 Key 校验走的是**主站域名** `modelscope.cn`，而生图走 `api-inference.modelscope.cn`。所以常见症状是「**生图一切正常，只有余额和校验 Key 报错**」。

这个坑很隐蔽，值得记住它的样子：`nslookup modelscope.cn` **能解析**，但程序 **报 ENOTFOUND** —— 因为 `nslookup` 绕过 `getaddrinfo`，直接向系统配置的 DNS 发查询，而 Node/libuv 走的是另一条路（本机实测 `dns.getServers()` 返回 `['127.0.0.1']`，即被代理工具接管）。**"nslookup 能通"不能证明程序能通。**

这里有两道保险，正常情况下你**不需要**做任何事：

- **候选域名回退**：请求按 `www.modelscope.cn` → `modelscope.cn` 依次尝试，成功后缓存。两者指向同一组 IP，所以换域名只是换一个解析目标 —— 实测过 A 解析不了而 B 正常的情况。只在**连接级**故障时才换（服务端已给出 4xx/5xx 就说明域名是对的，再换没有意义）。
- **DNS 兜底**：系统解析器解析不出来时用公共 DNS（同上一条）。

仍然失败时的排查（与上一条同思路）：
`node -e "require('dns').lookup('modelscope.cn',(e,a)=>console.log(e||a))"` —— 解析不通就重启代理 / 修 `hosts`。

**提示词明显没按官方规范来？**
按顺序排查三件事：

1. **类型选对了吗**。文生图规范产出英文长段观察式描述，编辑规范产出编辑指令 —— 两者完全不是一回事。改图请切「编辑图片提示词」。
2. **右侧「当前使用的规范」卡片**看文件名与 sha256。它显示的就是模型实际收到的文件；点「查看规范原文」可以直接读全文，和 `data/rules/` 里的文件比对。
3. **优化器模型换了吗**。规范文件是英文长指令（编辑规范 18 KB），指令跟随弱的模型会只学个大概。`optimizer.model` 留空则用默认的 `Qwen/Qwen3-8B`。

**历史里的图显示「图片文件已丢失」？**
`outputs/` 里对应文件不在了。提示词与参数仍然完整保留，可以按原参数重出 —— 这也是刻意不做自动清理的原因。

**端口被占用？**
`start.bat` 会识别占用进程并让你选择；或改 `PORT` 环境变量启动。

## 已知限制

- **多批并行是允许的**：同时运行的作业数上限默认 5（`MSQ_MAX_RUNNING` 可调），到上限才拒绝。并行意味着**多批各自计费**，请留意右栏「N 进行中」的提示
- **同提示词出的几张本来就会很像**。一批 4 张不是 4 个不同构图，而是同一构图的 4 次采样；想拉开差异得改提示词（优化器给出的描述尤其会把构图钉死）。界面的批内相似度只用来区分"像"与"真的是同一张"
- **「停止跟踪」不等于取消**。已提交给 ModelScope 的任务仍在执行，**额度不会退回**；界面上给的按钮就叫「停止跟踪」，不叫「取消」
- 一次最多 4 张。上限设得小是有意的 —— 每张各自计费，张数越大误触代价越高
- 生图历史全量读入内存后渲染，条目极多时（数千条以上）前端会变慢
- 无多用户与鉴权，设计上就是本机单用户工具
- **参考图经 ModelScope 推理 API 上限 4 张**（模型本身支持 10 张，见下）
- **无法从魔搭按关键词拉取 LoRA 列表**。`loras` 参数本身可用（界面已接入），但魔搭公开接口 `/openapi/v1/models` 会忽略全部查询参数、站内搜索接口需登录态，所以只能手工提供仓库 id（可粘贴社区链接自动解析）。见[LoRA 适配器](#lora-适配器)
- **LoRA 权重之和必须为 1.0，且需同底座底模**。接口不支持"少给一点"：id 写错会让整个请求失败
- 图片无法在界面上直接二次编辑，需下载后处理
- 提示词对话的上下文只取最近 6 条同类型消息，很长的迭代链会被截断
- 一次最多把 6 张图交给视觉模型，超出的按顺序丢弃（见[图片数量与体积上限](#图片数量与体积上限)）
- 官方模型卡给的 2K 宽高比（长边 2400~2752）**经此 API 不可达**，只有 1:1 2048² 能用，详见[尺寸预设](#尺寸预设)
- **透明图句式与主体提取不在两份官方规范里**，是项目自写的附加规则（默认关闭，按需勾选）。也就是说这两件事的提示词质量由本项目负责，不由官方规范背书
- **圈选标注也不在官方 edit 规范里**，而且情况更微妙：该规范要求「不要清理未被提及的 overlays」，标注线正属于 overlays —— 送去优化时模型可能反过来要求**保留**标注线。所以圈选提示词建议直接手写，或优化后人工确认「颜色逐个点名 + 结尾排除句」还在（见[局部重绘](#局部重绘蒙版画笔--圈选标注)）。**目前没有为它另立附加规则文件**
- **`ratio_follow` 未被消费**：规范返回的 `ratio_follow`（「输出跟随第 N 张输入图尺寸」）目前只显示标签、不会自动设置尺寸；只有 `wh_ratio` 会自动同步。编辑模式上传原图**不会**自动对齐原图尺寸（局部重绘会）。见[谁决定输出尺寸](#谁决定输出尺寸提示词里的比例还是页面的尺寸参数)
- **尺寸完全由页面参数决定**，提示词里的比例不会被解析也不会自动纠正；两者冲突时画布以页面为准、提示词里的横竖描述仍会被模型读作内容
- **DNS 兜底走的是直连，不经过代理隧道**。它只在系统解析器已经失败时触发（那时那条路本来就不通），但如果你的使用场景需要靠代理隐藏来源，这个兜底会绕开它 —— 请设 `MSQ_DNS_FALLBACK=off` 并去修本机 DNS。见[常见问题](#常见问题)
- **兜底也失败时不再重试**。同一个域名问两次没意义，反而白等十几秒；错误会立刻返回，并说明"本机与公共 DNS 都解析不出来"（那是断网或被防火墙整段拦了，不是 DNS 的毛病）

### 关于「10 张参考图」

官方模型卡明确写着 *Support up to **10 reference images*** —— 这是**模型自身的能力**，指的是本地 `QwenImage21Pipeline` 里 `image=` 传一个图片列表。而 **ModelScope 的免费推理 API 只放行 4 张**：第 5 张起在**提交阶段**就返回

```
400  image_url count 5 exceeds maximum limit of 4
```

这不是我们的实现限制，也不是 data URI 特有的问题（外链 URL 同样被计数拦下），而且换成 `images` / `reference_images` 等字段名也无法绕过 —— 那些字段名根本不被识别。

> **怎么确认「不被识别」的**：`images` 传 5 张时返回的是 **HTTP 200**（因为它不做张数校验），看起来像是"支持更多"。用同 prompt、同 seed 做三组对照即可拆穿：`image_url=[1张]` 出图 **2,138,462 字节**，`images=[1张]` 出图 **2,109,643 字节**，而**完全不带图**也是 **2,109,643 字节** —— `images` 与不带图逐字节完全相同，说明它从未被读取。**「不报错」在这个接口里不等于「生效」，这是最容易骗过自己的地方。**

**想真正用满 10 张，只有两条路**：本地跑 diffusers 管线，或改用其他托管服务（如阿里云百炼的商用接口，额度与限制另计）。本项目按 API 的实际能力把上限设为 4，并在超量时**当场提示**，不让它变成一个提交后才报错的暗坑。
